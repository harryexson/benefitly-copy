## Build fixed this pass (web)

`apps/web`'s `next build` did not succeed even before this session's changes (verified against a clean checkout of `main`). Five separate, unrelated defects were compounding; `next build` now completes cleanly, producing a full static/dynamic route manifest including `/_not-found`:

1. **Workspace package resolution.** `@benefitly/domain`, `@benefitly/validation` and `@benefitly/payments` import their own sibling files with explicit `.js` specifiers (required by their `"moduleResolution": "NodeNext"` `tsc` config), but the source files are `.ts`. Fixed with `config.resolve.extensionAlias` in `apps/web/next.config.ts`.
2. **PostCSS config collision.** `apps/web/app/globals.css` has zero Tailwind directives, but Next's config loader walked up to the repository-root `postcss.config.js` (owned by the legacy Vite app, written as an ES module without `"type": "module"`) and failed to load it. Fixed with a local `apps/web/postcss.config.js` (`{ plugins: {} }`).
3. **Build-time secret/DB requirements.** `lib/database.ts` and `lib/auth.ts` both threw at *module import time* when `DATABASE_URL`/`BETTER_AUTH_SECRET` were unset and `NODE_ENV === "production"` -- but `next build` always sets `NODE_ENV=production`. Both now use obviously-fake placeholders that fail loudly at *call* time instead.
4. **better-auth + Neon incompatibility.** better-auth's Kysely Postgres dialect issues plain `sql(text, params)` calls, a calling convention `@neondatabase/serverless` v1's `neon()` tag function removed. Fixed by passing a `Pool` (node-postgres-compatible) instead.
5. **Duplicate React instances.** `apps/mobile` (Expo SDK 53) pins `react` to exact `19.0.0`; `apps/web` depended on `react@^19.1.0`, forcing npm to install a second, nested `react`/`react-dom` inside `apps/web/node_modules` while `styled-jsx` (hoisted to the repo root) kept resolving the root copy -- two live React instances broke `styled-jsx`'s `useContext` call during static export of `/404`. Fixed by pinning `apps/web`'s `react`/`react-dom` to the same exact `19.0.0` so npm hoists one shared copy, and (incidentally, while diagnosing) pinning `next` to the known-good `15.3.9`.

Every web API route was then smoke-tested against a locally running production build (`next start`) with the placeholder `DATABASE_URL`: public pages return 200/404 correctly instead of crashing, and mutating routes that lacked their own try/catch now return a clean `503 SERVICE_UNAVAILABLE` JSON body via a new `withRouteErrorHandling` wrapper instead of Next's bare empty 500.

## Known gaps discovered and only partially fixed this pass

- **Missing `expo-router` dependency (`query-string`).** `expo-router`'s compiled entry (`getPathFromState-forks.js`) `require()`s `query-string`, which is not declared in `expo-router`'s own `package.json` dependencies. Fixed by adding it as a direct `apps/mobile` dependency.
- **Floating native dependency versions.** `react-native-screens` and `react-native-safe-area-context` are pulled in transitively by `expo-router`/`@react-navigation`, unpinned, and npm resolved them to versions well ahead of what Expo SDK 53 / React Native 0.79 shipped with (this environment's npm registry serves versions dated long after this SDK's actual release). Pinned both to their documented SDK 53 versions (`~4.10.0`, `~5.4.0`) as a direct dependency of `apps/mobile`, which is the correct fix in principle (this is what `expo install` automates) but network access to Expo's own version-compatibility API was blocked in this environment, so it could not be verified against Expo's real matrix.
- **`npx expo export` still fails**, even after the above, with a TypeScript-codegen parse error inside `react-native-screens`'s Fabric native-component specs (`Unknown prop type for "onAttached"/"type": "undefined"`). This looks like a further mismatch between the installed `babel-preset-expo` (resolved to `13.2.5`, transitively via `expo@53.0.27`, itself unpinned) and what SDK 53 expects (`~12.x`). Diagnosing and fixing this fully needs either a real device/simulator to verify against, or unblocked access to `expo-doctor`'s dependency-compatibility checks -- neither was available here. **This means the Expo app's TypeScript is verified correct, its API integration is complete and was code-reviewed, but it has not been confirmed to actually bundle or run.** This is the single highest-priority remaining item before any mobile work is trusted.

## Required external inputs

1. Neon pooled and direct connection URLs, database branch/deployment policy, and a designated migration runner.
2. `BETTER_AUTH_SECRET`, production web/mobile origins, email provider and sender domain.
3. Stripe secret key + webhook signing secret (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, optional `STRIPE_CONNECT_ACCOUNT_TYPE`); Adyen API key, HMAC key, merchant account and balance platform (`ADYEN_API_KEY`, `ADYEN_HMAC_KEY`, `ADYEN_MERCHANT_ACCOUNT`, `ADYEN_BALANCE_PLATFORM`, `ADYEN_ENVIRONMENT`) -- see `packages/payments/src/config.ts`. Connect mode/region policy, permitted payout countries and counsel/compliance sign-off per `docs/architecture/PAYMENT_PROVIDER_DECISION.md`.
4. Storage provider, malware-scanning policy, retention policy and secure-document access model (for campaign media/photo/video upload -- not yet implemented in either app).
5. Push/SMS provider credentials, EAS project/account ownership, Apple Developer and Google Play Console accounts, and a working `expo export`/EAS build in a real (non-sandboxed) environment.
6. Legal-approved privacy policy, terms, financial disclosures, charity/fundraising compliance rules, refund/dispute policy and support escalation process.
7. At least one `platform_admins` row (inserted manually against the production database) before any campaign can be approved, since Phase 1 requires manual review and there is no bootstrap admin UI yet.

## Still not built (explicit product requirements)

Camera/image picker and campaign photo/video upload (needs the storage-provider decision above first), push notifications, deep-link/universal-link testing, a real payout *approval* workflow (requests exist; approving and executing them does not yet have a UI), donation receipt emails, campaign-updates authoring, and EAS build profiles are unbuilt on both platforms. The full association-management module (members, dues, benefits/claims, events) has not been migrated off the legacy Vite/Base44 source at all.

## Release decision

Do not deploy, enable donations/payouts, submit to app stores, or claim production readiness. The next implementation sequence is: verify the Expo app actually bundles and runs on a real device/simulator (top priority -- see "Known gaps"); finish Neon schema/RLS and auth against a real database; migrate association workflows; obtain real Stripe/Adyen sandbox credentials, mount Stripe Elements/Adyen Drop-in on the donate screens, and run the guardrail checklist in `docs/architecture/PAYMENT_PROVIDER_DECISION.md`; build campaign photo/video upload, push notifications and the payout-approval UI; run the Gate 8 test suite; then remove the legacy provider code and publish a verified completion report.
